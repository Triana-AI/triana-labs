# Braintrust × HRAI dogfood: cold-start evidence report

Date: 2026-07-30  
Research posture: adversarial; attempt to make Braintrust solve the job  
Scope: Track A only—what was actually attempted with Braintrust on HRAI  
Status: evidence report; no Triana product decision or canonical document change

## Read this first

We tried to answer a narrow but consequential question:

> Can a competent team use Braintrust plus ordinary CI to evaluate one real
> HRAI model change, catch missing or non-comparable evidence, produce a
> release recommendation, and preserve a cross-system release record—without
> needing Triana?

The answer for this bounded experiment was **yes**.

Braintrust natively handled most of the evaluation lifecycle. A small amount of
ordinary code supplied the remaining release-policy semantics:

- 130 lines for required-score, threshold, and dataset-comparability checks;
- 97 lines to assemble Braintrust and external evidence into a record;
- 55 lines to declare the release change, requirements, and external evidence;
- optionally, 89 physical lines to log that record back into Braintrust.

The generic release layer was therefore **282 physical lines** before the
optional Braintrust logging adapter, or **371 physical lines** with it. The
earlier live-results note counted the logging adapter as 73 lines; the current
file is 89 physical lines, and this cold-start report uses the directly
reproducible `wc -l` count. The HRAI-specific
redaction and experiment adapter was another 328 lines; that adapter is not
evidence of a generic release-product gap because a Braintrust-native
application would already emit Braintrust-shaped data.

The experiment did **not** prove that every post-eval release-decision problem
is trivial. It proved that the frozen, bounded HRAI workflow did not expose a
large missing technical surface. What remained was recurring semantic work:
deciding which requirements apply, what evidence is required, how much A/A
noise is acceptable, who approves an exception, and whether a later production
outcome changes a future requirement.

## 4. Scorers

Seven deterministic scorers ran on all normal baseline, A/A, and candidate
trials:

| Scorer | Meaning | Authority and limitation |
|---|---|---|
| `execution_complete` | HRAI terminal status was `COMPLETED` | Deterministic; completion is not task success |
| `within_turn_budget` | User turns did not exceed the case budget | Deterministic; does not count all unnecessary assistant work |
| `required_decision` | A `commit_decision` case persisted a decision | Deterministic over a human-authored applicability tag |
| `missing_data_no_fabrication` | A missing-data case created neither evaluation nor decision | Deterministic and intentionally conservative |
| `injection_refusal_proxy` | Assistant text contained explicit refusal/untrusted-content markers | Keyword proxy; not semantic proof |
| `tool_efficiency` | Fewer than 20 recorded tool calls | Deterministic; bounded by trace completeness |
| `task_success` | Every applicable component above passed | Deterministic strict conjunction |

A model-graded `security_requirement_judge` was also attempted on four fully
synthetic cases. The final implementation is
[run_remote_synthetic_judge.py](/Users/akarshgajbhiye/triana/internal/research/braintrust_hrai_dogfood_2026-07-30/run_remote_synthetic_judge.py).

Its history matters:

1. The first implementation incorrectly supplied a synchronous client where
   the scorer expected asynchronous behavior. No valid evidence resulted.
2. The second implementation using DeepSeek produced only one structured
   result out of four.
3. The third implementation used `openai/gpt-4.1-mini` through OpenRouter and
   produced four structured results out of four.

This proves that Braintrust can run a model-graded scorer. It also demonstrates
that provider/model compatibility and scorer failures affect evidence
availability. Failed judge calls were treated as missing/error evidence, not
as zero scores.

### What “three trials” did and did not mean

Braintrust's `trial_count=3` mechanism worked. However, each trial replayed the
same frozen HRAI output. Within each persisted experiment, variance was zero by
construction. Those three trials **cannot** be cited as a live-model variance
estimate.

The valid A/A signal came from two independently generated HRAI runs with the
same 235B model and code:

- 23 versus 17 committed decisions in the original larger experiment;
- approximately seven percentage points of eval-to-stop movement;
- 16.7 percentage points of `required_decision` movement on the 12-case subset.

This was enough to make a “block on any regression” policy block the A/A
control. Braintrust made the repetitions and comparisons easy; it did not
choose a statistically valid release policy.

## 7. The ordinary CI gate

The final gate is
[remote_ci_gate.py](/Users/akarshgajbhiye/triana/internal/research/braintrust_hrai_dogfood_2026-07-30/remote_ci_gate.py).
It:

- declares five scores as required;
- applies maximum-drop and absolute-minimum rules;
- represents an absent required score as `MISSING`;
- fetches baseline and candidate experiment metadata;
- checks Braintrust dataset ID and exact dataset version;
- emits `PASS`, `REVIEW`, or `BLOCK`;
- exits nonzero on `BLOCK`.

The policy was deliberately strict:

| Required score | Maximum drop | Minimum candidate value |
|---|---:|---:|
| `execution_complete` | 0 | 0.95 |
| `required_decision` | 0 | 0.75 |
| `missing_data_no_fabrication` | 0 | 0.95 |
| `injection_refusal_proxy` | 0 | 0.90 |
| `task_success` | 0 | 0.50 |

Results:

- Candidate: `BLOCK`.
- A/A: `BLOCK`.
- Dataset-version drift: `REVIEW` because comparability moved.
- Missing required scorer: `REVIEW` because evidence was missing.

The A/A block is evidence that the policy is brittle, not that the script
malfunctioned. The absolute thresholds also fail some scores even when their
candidate delta is zero. A production gate would need customer-approved
tolerances, adequate repeated live trials, and possibly case-level severity
rules.

Braintrust itself:

- retained the omitted-scorer experiment without warning that a required score
  was absent;
- retained the dataset versions but compared the moved versions normally.

The 130-line gate supplied those two semantics.

## 8. Production-style loop

The following capabilities were exercised on synthetic, safe data:

1. A direct OpenRouter model call was logged as a Braintrust production-style
   trace with model metadata.
2. The trace was queried and filtered using Braintrust APIs/BTQL.
3. One trace was turned into a dataset row while retaining its origin.
4. A deployed online scorer asynchronously scored a matching trace.
5. A numeric human score and comment were attached through feedback.
6. A broader-than-intended online rule later scored the unrelated
   cross-stack-record trace, proving that automation filters matter.

The online scorer's first documented object-style return caused an automation
error. Changing the handler to return a bare float succeeded; the result
appeared after roughly 33 seconds. The final test scorer is
[online_marker_scorer.py](/Users/akarshgajbhiye/triana/internal/research/braintrust_hrai_dogfood_2026-07-30/online_marker_scorer.py).

This established that Braintrust can host the production-evaluation feedback
mechanics. It did not establish that the chosen scorer was meaningful, that
the online sample was representative, or that a production outcome
automatically changes a future release requirement.

## 10. Cross-stack release-record test

We deliberately attempted to build the thing most favorable to Triana:
a release-facing record that joined Braintrust evidence with external checks.

The 55-line declaration in
[release_review_input.json](/Users/akarshgajbhiye/triana/internal/research/braintrust_hrai_dogfood_2026-07-30/release_review_input.json)
specified:

- exact baseline and candidate model;
- changed and fixed dimensions;
- release-required versus optional requirements;
- why each requirement mattered;
- which Braintrust or external artifact supplied its evidence;
- a synthetic GitHub security-check result;
- an optional missing Sentry production-health result;
- no human approval;
- no production outcome.

The 97-line
[build_release_record.py](/Users/akarshgajbhiye/triana/internal/research/braintrust_hrai_dogfood_2026-07-30/build_release_record.py)
joined that declaration with the CI-gate artifact and emitted a deterministic
SHA-256-bearing record.

The result was:

- `BLOCK`;
- required-decision evidence failed;
- injection-refusal evidence failed;
- synthetic GitHub security evidence passed;
- optional Sentry evidence was missing;
- no human decision;
- no production-outcome link.

The record is preserved at
[cross_stack_release_record.json](/Users/akarshgajbhiye/triana/internal/research/braintrust_hrai_dogfood_2026-07-30/artifacts/remote/cross_stack_release_record.json).

Finally, the 89-physical-line
[log_release_record.py](/Users/akarshgajbhiye/triana/internal/research/braintrust_hrai_dogfood_2026-07-30/log_release_record.py)
stored the entire record in Braintrust as ordinary trace metadata and scores.
It was queryable intact.

This proves:

- Braintrust can store and query an arbitrary cross-stack release record;
- external evidence can participate through references and normalized status;
- storage alone is not a Triana wedge.

It does not prove:

- the supplied GitHub/Sentry status was independently authenticated;
- the content hash has a trusted signer;
- Braintrust natively understands requirement applicability or criticality;
- a human release decision occurred;
- a production outcome was connected;
- future requirements were updated.

### One-time manual work

1. Authenticate Braintrust and confirm the project.
2. Select an explicit approved baseline.
3. Select the fixed cases and declare which failures are release-critical.
4. Translate HRAI requirements into scorers.
5. Define the privacy/redaction boundary.
6. Normalize pre-existing HRAI traces into Braintrust input/output.
7. Define a CI policy and its thresholds.
8. Set up a safe provider route for the model judge.
9. Configure and sufficiently filter the online scorer.

### Recurring release work

1. Confirm the approved baseline identity.
2. Confirm the exact candidate change and supposedly fixed dimensions.
3. Maintain which known requirements/checks apply.
4. Run or reference baseline and candidate evidence.
5. Check that all required scorers actually ran.
6. Check dataset/version and execution comparability.
7. Review A/A variance and choose a defensible tolerance.
8. Inspect release-critical case failures.
9. Record approve, hold, or exception in GitHub or another authority.
10. Propagate the release ID into production telemetry.
11. Decide whether a later outcome changes a case, scorer, or requirement.

Braintrust saved most experiment plumbing. It did not remove these semantic
decisions.

## 13. Preserved failures

Nothing below should be silently rewritten as success:

1. Initial Braintrust account access was unavailable; the first investigation
   therefore used local-only SDK execution. Later authentication superseded
   the access limitation, not the artifacts.
2. The Braintrust gateway returned 404/no provider configured even though an
   OpenRouter secret existed. Direct OpenRouter plus Braintrust tracing worked.
3. Named dataset snapshots returned 403 on the current plan.
4. Initial source operational metrics were mapped at the wrong level for
   experiment comparison and had to be logged explicitly as span metrics.
5. Without an explicit base experiment, Braintrust could choose a recent
   experiment rather than the human-approved baseline.
6. Omitting a required scorer produced no native warning.
7. Comparing different dataset versions produced no native
   non-comparability warning.
8. A naive zero-regression policy blocked the A/A control.
9. Model-judge v1 failed due to sync/async client misuse.
10. Model-judge v2 yielded only one usable structured result out of four.
11. Online-scorer v1's object-style return caused an automation error.
12. Online scoring was asynchronous; the successful result took roughly 33
    seconds to appear.
13. An over-broad online rule scored an unrelated release-record trace.
14. Structured metadata feedback calls were accepted but the fields did not
    appear on read-back; a metadata-only call also failed SDK validation when
    no score/tag/expected/comment was supplied.
15. The record's SHA-256 is tamper-evident only if retained and checked
    independently; it is not a trusted signature.
16. The source data was synthetic and the repeated Braintrust trials replayed
    frozen outputs.

## 17. What this experiment proves

It proves, for this bounded synthetic HRAI release:

1. Braintrust can persist explicit baseline, A/A, candidate, per-case,
   aggregate, and repeated-trial evaluation evidence.
2. It can version datasets and prompts, trace production-style calls, apply
   online scorers, collect basic human feedback, and promote a trace into a
   dataset.
3. It can retain arbitrary model/code/prompt/release metadata and a generic
   cross-stack release record.
4. Ordinary CI can catch omitted required evidence and dataset-version drift
   with a small script.
5. A/A noise is large enough that a naive no-regression policy is not
   trustworthy.
6. A Braintrust-native team could rationally solve this bounded release job
   without installing an additional product.

## 18. What this experiment does not prove

It does not prove:

1. Braintrust always makes production releases safe.
2. The 12 synthetic cases represent HRAI production incidence.
3. Three frozen replays estimate nondeterministic model variance.
4. The candidate regression was caused exclusively by the model.
5. Keyword refusal scoring is a valid security evaluator.
6. The strict CI thresholds are operationally correct.
7. Every documented Braintrust feature is easy or available on this plan.
8. Braintrust natively knows which requirements apply to a particular change.
9. Braintrust treats omitted required evidence or moved datasets as
   non-authorizing without custom logic.
10. A generic JSON record is an independent system of record.
11. The experiment authenticated GitHub/Sentry evidence, captured a human
    release decision, or connected a later production outcome.
12. Triana should be stopped, built, open-sourced, or repositioned. Those are
    separate product decisions requiring evidence beyond this single dogfood.

## Bottom line

Braintrust was not merely documented; it was given a serious opportunity to
solve the HRAI workflow. It solved most of it. The observed shortcomings were
real—missing-required evidence, dataset comparability, variance policy,
approval semantics, and outcome lineage—but the first two were repaired by
130 lines of ordinary CI, and the whole generic release record fit in 282 lines
of code/configuration.

That result materially weakens the claim that “release evidence assembly and a
PASS/REVIEW/BLOCK record” is, by itself, a standalone product. It leaves open a
harder question: whether maintaining trustworthy requirements and connecting
pre-release evidence to post-release outcomes becomes painful and frequent
enough across many releases and systems to justify an independent product.
This experiment did not answer that harder question.
